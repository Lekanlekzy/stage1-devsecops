The official Gitleaks Action v3 uses Node 24 and supports current GitHub-hosted runners. The scanner version is separately fixed with `GITLEAKS_VERSION: 8.30.0`; the Action downloads or restores that release binary, so pinning the Action does not independently pin a scanner archive digest. Its [pinned implementation](https://github.com/gitleaks/gitleaks-action/blob/e0c47f4f8be36e29cdc102c57e68cb5cbf0e8d1e/src/index.js) uses commit ranges on PR/push events. An advisory full-history follow-up uses the installed binary and a positional repository argument; `git --source` is unsupported. Both scans use the central configuration extending built-in default rules, without project-ID exceptions. Both scan steps use step-level continuation; findings and Action/scanner errors are advisory, while checkout/configuration failures block. Native summary and redacted verbose logs provide results without custom classification. Comments and report-artifact upload are disabled; only `contents: read` and `pull-requests: read` are granted.

Gitleaks licensing depends on GitHub repository ownership: this personal-account setup needs no key; organization-owned repositories require an upstream `GITLEAKS_LICENSE` key, regardless of whether GitHub Enterprise is purchased. An enterprise-grade pipeline does not imply either account type. The current interface has no license mapping, so organization-owned callers require additional configuration before onboarding. See the [official Action documentation](https://github.com/gitleaks/gitleaks-action).

Trivy caching remains disabled in the workflow.

The two Azure actions use Node 24 on current GitHub-hosted runners in `reusable-app-cd.yml`. Only the CD caller and guarded deployment job permit `id-token: write`; CI needs no OIDC permission. Deployment authenticates with OIDC and a resource-scoped Azure identity after verifying the same-run ZIP checksum and revision. It has no source checkout, build/test commands, Sonar token, package-write token, or publish-profile secret. The deployment action receives the verified ZIP package through its `package` input; it does not build a container. See [Azure's deployment and OIDC documentation](https://learn.microsoft.com/en-us/azure/app-service/deploy-github-actions?tabs=openid). Cloud execution remains to be verified in the configured caller.

Prefer maintained official Actions for future tool integrations, verify their full commit SHA and required permissions, and check that their behavior preserves the central gates.

The OSV reusable workflow is restored at the user's request. Use the full-scan `osv-scanner-reusable.yml`, which covers current findings on pull requests, pushes, and manual runs; the `-pr.yml` variant compares new findings against a base revision. The pinned nested scan job declares `actions: read`, `contents: read`, and `security-events: write` regardless of `upload-sarif: false`. Both the central dependency job and its callers must allow those scopes. No other scan job needs security-event write access.

The wrapper SHA fixes its workflow definition, but upstream runs the scanner through a version-tagged container and does not set job timeouts. The wrapper pin alone therefore does not make every nested dependency immutable or give the upstream jobs a central timeout. Fixed scan arguments use `--recursive --no-ignore --no-call-analysis=all --config=/dev/null ./`. The empty-config override is supported by the pinned scanner's [TOML loader and override precedence](https://github.com/google/osv-scanner/blob/v2.6.0/internal/config/manager.go); that conclusion comes from source inspection, not a completed GitHub run.

An earlier direct-CLI experiment used the official Windows/amd64 v2.6.0 binary, verified against published SHA-256 `e0ed7644118b717b028c249ee9d3515024e55e8510747ca08906eb96765354d6`, and returned vulnerability findings. That historical smoke test is not a pass and does not validate the restored reusable workflow. Review the pinned upstream workflow, its scanner version, and permissions together when updating the Action reference. GitHub execution of the restored dependency workflow remains unverified.
